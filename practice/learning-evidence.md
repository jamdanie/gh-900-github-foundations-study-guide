# Show what you actually learned

[Table of contents](../CONTENTS.md)

A useful study artifact lets someone understand what you did, what happened, and what you concluded. It can be a small note with a graph, a reviewed PR, or a workflow result.

## Separate the activity from the claim

| Activity | Evidence to keep | What it supports |
| --- | --- | --- |
| Browser Git simulator | Starting graph, action, final graph, explanation | Understanding demonstrated within that exercise |
| Local Git lab | Commands, relevant history output, resulting files | A local workflow you performed |
| GitHub PR | Diff, review reasoning, applicable check results | A proposed change you inspected |
| Steam simulation | Your observation and clearly labeled screenshot | Behavior observed in that game |
| AI-assisted explanation | Verified source and your own application of the concept | A learning process, not proof that AI's first answer was right |

## Write a result someone can follow

State the task, the action you actually performed, the observed result, and the limitation. For example, after completing the local graph lab, you could explain that you created separate note files on two branches, merged them, and inspected the resulting history. Only say the merge succeeded if you observed it.

For a game-based note, identify the title and keep the scope explicit: a simulated fault was investigated in a game. Do not describe it as repairing a real server.

## Make the artifact easy to review

Link the relevant note or PR, explain a screenshot in text, and remove unrelated output. Give a diagram meaningful labels. Check that a reader can distinguish your prediction from the result.

Use your [review log](review-log.md) for unfinished learning. A contribution count records activity; the explanation and evidence show what the activity accomplished.
